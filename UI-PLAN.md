# Web UI plan

A small web app for monitoring and acting on the reviewer, on the owner's own machine.

## Decisions

| Area | Decision |
|---|---|
| Access | Served on the owner's machine in one of two modes (`web.mode`). Local: http://127.0.0.1:8470 (`web.port`). Tailscale: a unix socket published with `tailscale serve` (HTTPS), so the owner's other devices and phone can reach it. With no mode set, a config with `web.allowed_login` gets Tailscale and any other gets local. |
| Auth | Local: `bin/plus1 open` mints a one-time sign-in link good for 5 minutes; signing in sets an HttpOnly session cookie good for 30 days, derived from a secret that never leaves the state folder, and every request must name a loopback host. Tailscale: only the owner's tailnet login (`Tailscale-User-Login` header from `tailscale serve`) is accepted, and other tailnet users get 403. A CSRF token on every action in both modes. |
| Stack | Python server, server-rendered HTML with htmx, server-sent events for live updates. No build step. Reuses the `plus1` modules so the UI and CLI share one code path. |
| Storage | SQLite (`<state_dir>/prr.db`, default `~/.local/state/plus1/`, WAL) records runs, per-PR observations, reviews, stages, findings, drafts, actions, grades and live events. |
| Captured per review | Reviewer output and coverage, every finding with the verifier's verdict (including dropped ones), cost, tokens and duration per stage, and the diff snapshot at the reviewed SHA. |
| Navigation | Sidebar with To do (decision rows, live counts, and a pill when a check finds new or updated PRs), Activity (what it did and is doing, grouped by day, marking where the owner left off, one row per PR with earlier reviews folded under the latest, and who opened each), Insights (an advisory readiness checklist per repo, agreement, this week, spend, recent checks with runs of quiet ones folded into one line), Grade (under Tuning, with a gray count of past decisions waiting for a grade, leaving out PRs still on To do), Rubric changes, and Settings. The sidebar shows "Auto-approve" when any repository approves on its own and "You approve" otherwise, the next check inside the working window, today's spend with "cap of $X reached" once the daily cap is hit, and "Slack off since" when Slack cannot be read. With more than one repo configured, every PR is labeled with its repo's short name, for example `api#123`. Bottom tab bar on phones, with Review a PR as a + in the top bar. Command menu on ⌘K, keyboard shortcuts under `?`. |
| Home | At 1100px and wider, a two-pane inbox: list left, selected PR review right. Clicking a row or pressing J/K selects it and updates `/review/<id>`, preserving the selection across refresh, back, and links. Acting selects the next PR immediately; the acted row keeps its countdown and Undo until the action lands. Narrower layouts use collapsible rows grouped as ready to approve, blocking, worth fixing, needs a look, couldn't review, and new commits. A PR with commits newer than its review files under new commits regardless of the call, since it cannot be approved or posted until Review again runs. A stack files under its most urgent part. PRs titled `[n/m] (TICKET)` share one stack row. Each row shows the title and source, then who opened it, why it waits (the top comment's point, what a Needs a look PR touches, or what a ready PR does), and its age. An agent's PR names its requester and says it came through an agent. Only the first row starts open. It leads with the decision ("Approve with 2 comments?") and main button, then the reviewer's account of what the PR does and why, its ticket in the repo's issue tracker and stack position, the problem, and each comment with code one click away. Lane, size, and agent-written appear only when they change the call. Files, checks, and private notes fold behind Details. On a phone, acting collapses the row and opens the next. PRs with a personal request for the owner, enough changed or removed lines written by the owner, or 2 owner commits in the last 6 months to a changed file move up one review tier, never ahead of follow-ups, and sort first in their To do group. Their rows show an "asked you", "your code", or "your files" chip for each matching signal, and their cards explain each signal in a sentence. |
| PR page | Title with GitHub and history links, then who opened it, the ticket, stack position, size, review time, and the card. Each comment folds what the reviewer saw, why it matters, and how it was double-checked. A clean Needs a look PR, held only by its lane, leads with Approve, lists private notes, and opens the code with every file that prevented automatic approval. Collapsed sections show the stack's parts, reasoning with any finding lacking a comment, code around the comment with the full diff one click away, and behind the scenes: grading, lane, commit, timing, cost, what happened after, dropped findings, and private notes. A PR still on To do opens in the inbox; any other review stands alone under Activity. `file:line` mentions link to the diff or GitHub at the reviewed commit. A sticky action bar with Next follows To do order. |
| Actions | Request changes with a blocking comment, approve with or without comment, don't post, mark as handled, I'd comment, review again, edit, rewrite with a suggestion (the rewrite waits under the comment until the owner uses or drops it), let someone else review (checks skip it until the owner brings it back from Activity), and "It's right, allow posting" for a fact-check-flagged comment. Posting and approving, and Don't post, Review it again at the next check, Mark as handled, and Let someone else review, wait 8 seconds on the server with Undo. Edits and rewrites change the comment at once. Posting is refused on stale commits and flagged comments. They run on the server, so closing the app during the countdown is safe. A failed or expired action sends a notification and stays on its card until a newer review. A post refused for new commits also starts a review of them, and the card says so until that review finishes. |
| Live view | Stage progress per PR (triage, deep review, verifying 2 of 3, drafting) with elapsed time and running cost. |
| Calibration | Grade queues 12 ungraded past decisions, putting approvals first for repositories whose readiness checklist still needs graded approvals until it has 30 or more, followed by comment drafts that would put words in the owner's name, other approvals, and decisions left to the owner, excluding PRs still on To do. A strip marks every decision right, wrong, skipped, current, or still to come, with "N of 12 in this queue" and how many more are waiting. Keys are Y for right call, N for wrong call with what went wrong (1 to 8), and S for skip. The page address keeps the queue, so refresh and Back keep its place. Completion summarizes right calls, wrong calls with reasons, skips, graded approvals, false approvals, checklist agreement, and what the queue added. It offers Start another queue, which leaves out what was skipped, or Back to To do. Owner actions on GitHub provide automatic comparisons. Manual grades and reason tags cover the rest. Bot-posted reviews are excluded. Not posting a comment prompts an optional one-tap reason. |
| Readiness checklist | Insights shows each repository's advisory checklist: 5 working days, 30 or more graded approvals, zero false approvals, at least 90% agreement, plus estimated working days left at the recent pace. It does not block the setting. The graded-approvals line and Grade them row open the grade queue with the count still needed. Insights links to Settings, which shows items met and turns the setting on with typed `loosen`, or off without confirmation. |
| Settings | Settings is a dedicated page in the sidebar and command menu. It groups settings by what they do, because the owner looks for a setting by the question they have: Checking contains Schedule, Sources, Waits and skips, and Budget; Approving on its own contains one section per repo, Every repo, and Limits; Reviewing contains Rubric, Models, and Repos; Notifications manages desktop and registered devices; System contains You, Web app, Files, Updates, and Recent changes. A status strip shows checking state, next check, today's spend against the cap, and each repo's approver, with a switch to pause or resume checks. At widths of 1200px or more, a sticky section rail follows scrolling and provides a filter focused by `/`; narrower layouts use a grouped index showing current values and a sticky crumb. Sections save independently. Dirty sections reveal Save and Discard. Nondefault values expose their default and Reset. Saving edits `~/.config/plus1/config.toml` in place, preserves comments, writes only changed values, removes values reset to defaults, retains `config.toml.bak`, and restores it when the result fails to load. Checks use saved changes on the next run, and the app detects hand edits. Built-in never-approve paths, skip labels, and blocking markers render as locked entries. The server determines typed confirmations: autonomy increases show before and after values and require `loosen`; machine execution changes show commands split into exact arguments and require `run`; serving mode, allowed login, and socket changes require the new value again. Web app settings and the history folder remain pending until restart; the page identifies pending values, offers Restart web app, and shows the `sudo tailscale serve` command after a socket move. Repo clones must be git clones whose origin matches the GitHub repo. Add repo suggests repos from review requests and finds clones; new repos start with autonomous approval off; removal preserves reviews and history. The rubric opens on its own page with diff preview, records a revertible rubric change, and can relearn GitHub reviews for about $1. Recent changes records every save and the value it replaced. Each repository's Approving on its own section includes a Hold PRs in your code switch. It is on by default, and turning it off requires typing `loosen`. Settings, You, lists under Commit emails the addresses found from git's user.email and from GitHub, where the owner can add more. The GitHub noreply address always counts. Settings, You, also has three chip lists: Your teams (`org/team`), People (GitHub logins), and Other teams (`org/team`, for teams the owner isn't on but still wants to review). Each team row shows how many people it last read or why it couldn't, and offers suggestions from GitHub when its panel opens. Within each To do group, PRs from the owner's team lead with a "team" chip, then other teams' with a "watching" chip, then PRs in the owner's own code. Settings, Updates, chooses Automatic, Ask first, or Off and whether to follow releases or main, shows what's installed and latest, and offers Check now, Install, Roll back, and the history. |
| What's new | The sidebar's version opens What's new, the release notes from this copy's changelog. After an update, open tabs reload themselves and say what happened, or show a Reload button when something is unsaved. |
| Extras | Review a PR on demand (by number, or a pull request link from any configured repo), turn a disagreement into a proposed rubric edit (the owner approves before their `rubric.md` changes), rubric changes learned from the owner's GitHub reviews (`bin/plus1 learn`) and drafted on their own when the owner's GitHub review differs from a call, per-PR story page, weekly summary. |
| Notifications | Desktop notification that opens the item (`notify-send` on Linux; `terminal-notifier`, else a plain notification, on macOS), plus Web Push to the phone from the installed home-screen app in Tailscale mode. |
| Look | Linear-style: inset content panel, Inter (self-hosted), neutral grays with one indigo accent, status shown as small icons and dots. Follows OS light or dark. Responsive down to phone width. |

## Build order

All four phases are built: capture (SQLite and per-stage usage), the read-only views, actions with confirm and the draft editor, then calibration, the readiness checklist, rubric proposals, the PR story, the weekly summary and Web Push.
