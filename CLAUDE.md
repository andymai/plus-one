# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Plus One is an unattended reviewer that each engineer runs on their own machine for the PRs waiting on them (its owner): silent approval of clean PRs in repos where the owner turns it on, queued comment drafts for P0 and P1 findings, `DEFER` for everything else. `README.md` has the command table and quick start, `docs/onboarding.md` the setup and first week for an engineer, `docs/admin.md` running it for a team, `DESIGN.md` the decisions and per-tick pipeline, `UI-PLAN.md` the web app, and the owner's own `rubric.md` (learned from their GitHub reviews, starting from `plus1/starter_rubric.md`) what the reviewer looks for.

## Commands

```bash
uv sync                                                                 # .venv from uv.lock, dev tools included
uv run prek install                                                     # once per clone: lint, format, types, and commit message on every commit
.venv/bin/python -m unittest discover -s tests                         # all tests, no network, about 20s
uv run coverage run -m unittest discover -s tests && uv run coverage report  # with the coverage floor CI enforces
uv run ruff format && uv run ruff check                                 # format and lint, which CI checks
uv run basedpyright                                                     # type check, which CI runs
uv run lint-imports && uv run vulture                                   # import boundary and dead code, which CI checks
.venv/bin/python -m unittest tests.test_core.CodeownersTest.test_globstar  # one test
.venv/bin/python tests/selftest_sandbox.py                              # live sandbox check, costs a few cents
bin/plus1 tick --plan --any-time                                        # live GitHub, filters and lanes only, no model calls
bin/plus1-web --tcp 127.0.0.1:8000 --dev-login                          # web app on loopback, no Tailscale needed
```

Unit tests read `tests/config.toml` (each test module sets `PLUS1_CONFIG`); everything else reads `~/.config/plus1/config.toml`.

`ruff format` (100 columns) formats Python and `ruff check` lints it, both configured in `pyproject.toml`, and CI fails on either. A rule is turned off for one line with `# noqa: CODE (why)`, and the file-wide exceptions in `pyproject.toml` each say why. basedpyright checks types in standard mode with no errors allowed; tests skip only its optional-access rules, since a `None` there fails the test anyway. CI runs the tests on Python 3.11 and 3.14 and fails below `fail_under` in `[tool.coverage.report]`, which only goes up. Only `plus1.web` imports `plus1.web` (import-linter's protected contract in `pyproject.toml`), so the CLI, the tick, and setup run without the web app. vulture looks for dead code at 60% confidence; a name only the templates or the stdlib use goes in `vulture_whitelist.py`. The hooks in `.pre-commit-config.yaml` run the same locked tools through prek, and `scripts/commit_msg.py` accepts the same types as `.github/workflows/pr-title.yml`. Python 3.11+ (`tomllib`); the venv runs 3.14. `--dev-login` (which works in either web mode) reads the real state dir unless `PLUS1_CONFIG` points at a config with another `state_dir`. It skips the background executor and the GitHub status watcher, but loading `/` runs due card actions through the real `gh`, so a clicked Post or Approve still reaches GitHub. Put stub `gh` and `systemd-run` scripts first on `PATH` before clicking through actions locally. Launch the web app through `bin/plus1-web`, not `python -m plus1.web.app`: running `app.py` as `__main__` gives `HttpError` a second identity that `dispatch()` can't catch.

`bin/plus1 install` (`plus1/units.py`) writes services that run straight from the checkout it ran from: systemd user units on Linux (`~/.config/systemd/user/`, replacing older links into the repo), launchd agents on macOS (`~/Library/LaunchAgents/local.plus1.*.plist`, logging to `<state_dir>/logs/`), each with the PATH `host.service_path` finds and any `PLUS1_CONFIG` set at install time. The timer fires every 30 minutes and the tick keeps to `[window]`, so the next tick runs whatever is on disk here. The web service keeps the code it started with until restarted (`systemctl --user restart plus1-web.service`, or rerun `bin/plus1 install`), which automatic updates do for you (see Keeping itself up to date). Parallel branches go in `.worktrees/` (gitignored), which keeps unfinished work away from the live bot.

Releases come from release-please (`release-please-config.json`, `.github/workflows/release.yml`): merged Conventional Commits (a `Release-As: x.y.z` footer picks the version) accumulate in a release PR that bumps `__version__` in `plus1/__init__.py` (the line marked `x-release-please-version`) and `CHANGELOG.md`, and auto-merges once CI passes, which tags the release. It runs with the GitHub App token (the release-kun App: `RELEASE_KUN_APP_ID`, `RELEASE_KUN_APP_PRIVATE_KEY`), since a PR opened with `GITHUB_TOKEN` never triggers CI. Installs follow `updates.channel`, the release tags by default. `bin/plus1 --version`, `doctor`, `update`, and the sidebar show the version. Dependabot updates `uv.lock` but not `requirements.lock`, so `.github/workflows/dependabot-lockfile.yml` commits a fresh export to its PRs with the same app, whose secrets are set as Dependabot secrets as well. The owner's `release-kun-secrets andymai/plus-one` sets all four from 1Password.

## Onboarding

`bin/plus1` and `bin/plus1-web` both run `bin/ensure-venv`, which sets up `.venv` on first run (uv, which reads `.python-version` and fetches that Python, else the newest `python3.1x` at 3.11 or later), and syncs the dependencies to the lock whenever its hash differs from the one recorded in `.venv/.plus1-lock` or one doesn't import (`uv sync --frozen --no-dev --inexact`, else pip with the hash-pinned `requirements.lock`), so a fresh clone needs only `bin/plus1 setup`, an install cut short recovers, and the web service picks up a dependency an update added. Dependencies are declared in `pyproject.toml` and locked in `uv.lock` (`exclude-newer` keeps resolution a week behind PyPI); after changing either, run `uv lock` and regenerate `requirements.lock` with the `uv export` command in its header, which CI checks. `setup.run` asks one question at a time through `setup.Prompt` (tests script it with `Scripted`) and works before any config exists, so `cli.main` runs it, like `update`, without loading one. It suggests repos from the owner's review requests and recent reviews (`setup.suggest_repos`), finds each clone by its `origin` under the usual code folders (`setup.find_checkout`), and suggests never-approve teams (`setup.gate_teams`: any team an approval-gate check names, and CODEOWNERS teams whose names read like a gate); the owner keeps or drops each. It offers the owner's GitHub teams in those repos' orgs for `team.teams` (`team.suggest_mine`). Zone and hours are re-asked until valid, a failed GitHub search falls back to typing repos, and a found clone is skipped only by typing skip. It writes the config (`setup.render`, keeping any old one as a `.bak`), copies the starter rubric when there's none, offers `learn`, runs `units.install`, and opens the web app signed in only when it was installed. `bin/plus1 doctor` (`doctor.checks`) checks tools, logins, repo access, clones, the rubric, that the timer is active (`units.active`), the web app, and the last tick, each failure with its fix. `bin/plus1 update` installs through `updates.run` (see Keeping itself up to date). When the config doesn't load, `doctor._pull` pulls with `--ff-only`, runs `bin/ensure-venv`, and reinstalls the timer and web app as installed, or only restarts a web app installed alone, so a bad config can't strand an install.

## Architecture

### Config (`plus1/config.py`)

Two layers: `plus1/defaults.toml`, then personal config at `~/.config/plus1/config.toml` (`PLUS1_CONFIG` overrides the path, `XDG_CONFIG_HOME` its directory), whose top level and each `[[repos]]` entry can set `[lanes]` and `[filters]`. Personal config overrides any default, but the lists in `config.ADDITIVE` (never-approve owners and paths, hold labels, blocking markers) are unions across the defaults, the top level, and the repo entry, so no config can drop a default safety lane; any other key in those sections (`filters.approval_gates`) takes the last that sets it. Nothing in the repo is specific to one company: a repo's gate teams, doc paths, and issue tracker live in its `[[repos]]` entry. The defaults put files that instruct the reviewer (`CLAUDE.md`, `AGENTS.md`, `.claude/`) in the never-approve lane, since the review runs in the PR's own checkout. Each `[[repos]]` entry resolves to `cfg.repos[n]` with its own checkout, peers, issue tracker, checks, `auto_approve`, lanes, and filters, and the first one is mirrored onto `cfg.repo`, `cfg.checkout`, `cfg.peers`, `cfg.issues`, `cfg.lanes`, and `cfg.filters`. Code that works on one PR uses `config.view(cfg, name)` (or `config.at(cfg, pr_id)`), a copy of `cfg` whose mirrored fields are that repo's, so `gh` calls and lanes always read the PR's own repo. `name` (how prompts and drafts refer to the owner) defaults to `me`, and `timezone` to the machine's zone.

### PR ids (`plus1/prs.py`)

One instance reviews several repos, so every table keys a PR by one integer: the repo's id in the `repos` table times `prs.BASE` plus the GitHub number. The first repo registered takes id 0, so an instance that started with one repo keeps its stored numbers. `Store.__init__` registers the configured repos and swaps in fresh lookups (`prs.pid`, `split`, `number`, `repo`, `url`) under a lock, since web threads read them while another opens a Store. A repo taken out of the config keeps its rows and its review pages, but `cards.refresh_status` stops polling it. Searches match a PR by its GitHub number (`queries._number`: `123`, `#123`, or `api#123`). `prs.label` is `#123` while one repo is configured and `api#123` once there are more; templates use the `prnum`, `prlabel`, and `prurl` filters, never the raw id. CLI PR arguments take `123` (the first repo) or `owner/repo#123` (`cli.pr_id`), and review-now in the web app takes a number or a link from any configured repo.

### Tick pipeline (`plus1/cli.py:tick`)

1. Guards: `PAUSE` file, working window from `[window]` (`--any-time` bypasses), then for a timer tick a random wait of up to `window.jitter_minutes` (`cli.jitter`, so teammates' instances don't review the same team request in lockstep), then `flock` on `tick.lock`.
2. Candidates, gathered per configured repo (`cli.gather`, where one repo's failed review-request or follow-up search doesn't stop the others): `gh.candidates` (review requests), `gh.followups` (open PRs the owner reviewed whose overall decision is Changes requested), and `slack.announced` (PR links in team channels, best effort since the token expires daily). `slack._token` reads `slack.token_path`, one Claude credentials file or a list of them (one per Claude login that uses Slack), and uses the copy that expires last, since Slack revokes a person's older tokens for the app whenever it issues one of them a new token. GitHub drops the owner from a PR's requested reviewers once they review, so without `gh.followups` a PR they blocked would never come back after the author pushes. After fetching, `filters.followup` marks a PR whose owner's latest decisive review is Changes requested, with that commit (empty when a force-push left the review without one, which skips the unchanged-files shortcut), the review body, and the owner's threads that are unresolved or that someone else resolved (outdated ones included), since an author marking a thread resolved doesn't show it's fixed. On a follow-up the owner's own blocking threads don't trigger the open-blocking-thread skip, since they are the asks it checks. Follow-ups sort first, then PRs from both other sources.
3. `gh.fetch_pr` (one GraphQL query, flattened by `gh.normalize`), then `filters.evaluate` returns `Skip("skip" | "defer", reason)` or `None`. `filters.lane` assigns `dependabot` or `never_approve` from the PR's repo's CODEOWNERS (fetched for each repo every tick, matched by `codeowners.py`) and `[lanes]` path regexes. `lane_reason` names only the first hit, so `filters.sensitive` stores every hit as `reviews.sensitive` for the review page. A `None` lane means the model triages. Handed-off PRs are skipped before fetching, except one handed off at least `limits.handoff_working_days` working days ago: it's fetched, and when it's still open, not approved, and nobody besides its author has reviewed it since (`filters.picked_up`, from each review's `submittedAt`), it comes back, recorded as a `resurface` action that flags its card "nobody picked this up". A filter `defer` (diff over `max_map_lines`) still records a `DEFER` review without any model call, and `--force` overrides only `skip`. Checks whose names match `filters.approval_gates` (approval gates such as "Require security-reviewers Approval", which fail until someone approves) never count as CI. Fetches run in parallel, and reviews run one at a time up to `max_reviews_per_tick`. Before each review a tick (not a `--pr` run) stops starting reviews once `Store.spend_today` (every model call today, from `stages`) reaches `limits.max_spend_per_day_usd`, observing the rest as waiting, and skips a PR GitHub now reports approved, merged, or in the merge queue (`cli.fresh_state`), unless it's a follow-up. A PR passed over because the budget ran out is observed as `waiting`, and each such observation at its head moves it up one tier in `cli.priority` (`Store.waits`), so a Slack-only PR can't starve; Activity's skipped view lists it as waiting for a review slot. Before ordering, `yours.gather` (`plus1/yours.py`) reads what the owner has to do with each eligible PR: who asked them by name (`gh.normalize`'s `requests`, leaving out bots and the owner), how many of the lines it changes or removes blame gives to them (at the merge-base, through the repo's `.git-blame-ignore-revs`), and which changed files they made 2 or more commits to in 6 months on the base branch, leaving out lockfiles and schema dumps (`yours.GENERATED`). `yours.matcher` knows the owner by config's `emails`, git's `user.email` in each clone, the authors GitHub matched to their login (`gh.commit_emails`, refreshed daily into the `yours_emails` meta row), and their noreply address. Git's part is kept per commit in the `yours` table and copied onto `reviews.yours`. Any signal (`yours.kinds`) moves a PR up one tier in `cli.priority`, never past follow-ups, and the tick's notification counts the PRs with one that still need the owner. `team.refresh` (`plus1/team.py`) runs on every check, with or without eligible PRs, and reads the GitHub teams in config's `[team]` into one `team_members:<org/team>` meta row per team, so a slow read can't overwrite another team's. It reads each once a day and a new one at once, keeping the last members when a read fails. `team.kind` marks a PR `team` when its author, or the person behind an agent PR, is on `team.teams` or `team.people`, and `other` for `team.others`. Either moves it up one tier in `cli.priority`, the same single tier a `yours` signal gives, and the notification counts the `team` ones that still need the owner, which can send it alone. The team only orders PRs that already arrived: it adds no candidates and touches no gate.
4. `review.run`: throwaway worktree of the PR head under `<state_dir>/work/`, created from the `checkout` repo. Before a tick's first review of each repo, `peers.refresh` fetches the default branch of each repo in that entry's `peers` and checks it out in that repo's snapshot under `<state_dir>/peers/` (a failed fetch keeps the last snapshot, and a repo it can't set up is left out). The deep review and verifier can read those snapshots, and the rubric's rule for a reader in another repo sends them there. Then triage (no tools) when the lane is `None`, the repo entry's `checks` (`review.run_checks`: commands the owner opted into, such as `bin/packwerk check {files}`, run by Plus One in the worktree with fixed arguments, no shell, the reviewer's stripped environment, and `limits.check_timeout_s`; `{files}` expands to the changed files that exist, from git when GitHub's list stops at 100, leaving out any name starting with a dash; only the last 4000 characters of output are kept as it arrives, decoded with replacement and kept on a timeout), the deep review with their output fenced in `check_output` tags as data, and one verify call per finding. The reviewer's own tools stay read-only: it never chooses what runs, since a model that reads PR text could pick arguments that run anything. Teardown stops anything still running from inside the worktree (`review.stop_leftovers`, from `/proc` or `lsof`), since a check can leave a daemon behind, as Spring does. The deep review prompt carries the GitHub discussion (`prompts.discussion`: unresolved threads on current code, human review bodies, human PR comments, with `<details>` and HTML comments stripped and the whole capped at `DISCUSSION_CHARS`, fenced in `github_discussion` tags that comment text can't close). The reviewer checks other reviewers' claims like its own, sets a finding's `raised_by` when an open thread already raised it (kept only for a login on an open thread, `filters.thread_authors`; the draft then agrees with them, without an @), and lists in `waiting_on` anyone still owed an answer or a change. Unverified findings become private P2 notes. A finding the owner chose not to post on any review of the PR (its draft `dismissed`, gathered by `Store.waived`) stays waived: neither it nor a later review's copy of it (matched by title) carries forward, the prompt lists it as declined (`prompts._waived`), and a new finding with the same title becomes a note. On a follow-up, the owner's open threads and Changes-requested body come first among the earlier findings as P0 claims (`origin = 'owner'`, prompt text from `prompts.asked`), followed by the last review's verified findings whose drafts never posted (a posted one is already an owner thread), which carry and draft as usual. An ask stays open when a continuation or its re-verification holds, and is fixed otherwise, and an ask is never drafted, since the comment is already on GitHub. A new finding with `raised_by` set to the owner is a duplicate of their thread and becomes a note. When git shows the PR's own files unchanged since the owner's commit, the result is `DEFER` with `FOLLOWUP_UNCHANGED` and no model call. `Reviewed.followup` records each ask with its thread id and whether it's still open, and is stored as `reviews.followup`. GitHub returns the first 100 threads, so when there are more the record gains an always-open `review.UNCHECKED` ask and nothing can read as all fixed. A re-review gets the PR's last model-run review (`Store.prior_review`, which skips filter defers and failed runs). `review._moved` compares the two commits' `git diff --raw -z` listings (blob hashes and modes, read as bytes, from each commit's merge-base with the base branch), so nothing written into a line can make changed code look the same; a rebase moves nothing unless the base changed the PR's own files. With nothing moved, a `DEFER` (other than an open-comments hold) carries to the new head with no model call, and so does an `APPROVE` that clears the gates a fresh one would: not the `never_approve` lane, and nobody `filters.could_hold`. When some files moved, the PR isn't too large, `diffs.interdiff` sizes the text change under `incremental_max_lines`, and that review was a thorough `APPROVE` or `DRAFT`, the deep review gets `since.diff` (the change between the two commits in exactly the moved files) and reviews only that. Anything else, a comparison git can't make, a PR whose base branch changed since that review, and any review at the same commit run in full. The earlier findings and the earlier summary go into the prompt inside `earlier_review` tags their own text can't close, as data rather than instructions. The review's verified findings carry forward too. A finding that carries one forward sets `continues`, can't drop below its earlier severity, and inherits its `raised_by`. Every earlier finding that no verified continuation holds (left out, or reworded and then rejected) is verified again on the new head as first written, so only the verifier can let one go (noted as "fixed since the last review"). A PR over `max_diff_lines`, or whose file list GitHub cut off at 100 (`filters.too_large`), is mapped instead of traced: the prompt points the reviewer at the riskiest code and `MAP_SCHEMA` adds `focus` (where the owner should look first, which leads the card and the pane's code section). The verdict stays `DEFER` unless a finding survives verification. Lanes still come from GitHub's first 100 files, which can't cost an approval since a large PR never approves.
5. `cli.handle`: stores findings. For `DRAFT`, `drafts.py` writes each comment with the `draft` model role, or through the external `draft_command` script when one is set (its exit code 1 means a dash slipped in). A dash in either retries once with a rule against it. Then a `factcheck` call (no tools) checks the text against the finding. A flagged comment gets `needs_edit`, which `release` refuses until it is edited or allowed. If drafting fails, the raw finding text is stored marked `DRAFT_FAILED`, which only an edit clears. `diffs.anchor` places each comment on a right-side diff line, or in the review body when the line isn't in the diff. `APPROVE` calls `actions.approve` only on a timer tick in a repo that approves on its own (see Approving on its own), under the per-tick and per-day caps, and never for a follow-up: lifting the owner's own Changes requested is always their call. `cli.yours_hold` holds an automatic approval in a repo whose `hold_yours` is on (the default) when `yours.hold` finds the owner asked by name, 20 or more of their lines changed (or a quarter of at least 5), or git couldn't be read; their recent commits alone never hold. `cli.hold` also asks GitHub once more right before an automatic approval and holds it when the PR is already approved or merged, or when GitHub can't be asked. An approval held back by a pause, a hand-off, a cap, or a Changes requested still standing on GitHub (the PR's overall decision, which also catches an owner's block older than the 50 reviews fetched) is recorded on the review as `reviews.held`, which flags its Ready to approve card. Each later timer tick's `retry_held` skips one the owner settled (a `handled` row: I'd comment, Mark as handled), re-fetches the rest and approves only when `regate` finds it still at the reviewed head and through every gate a fresh approval faces (`filters.evaluate`, the lane, a follow-up, `filters.could_hold`, `yours_hold`), so a retry can't skip what changed since. Anything else updates `held` with the reason.
6. Calibration: `calibrate.infer_from_actions` and `calibrate.sync_github` grade past reviews against what the owner did in the app and on GitHub. `calibrate.stats` turns those grades into the checklist for approving on its own.

### Learning the owner's rubric (`plus1/learn.py`)

`bin/plus1 learn` reads the owner's own reviews from GitHub (`learn.reviewed`: `gh search prs --reviewed-by @me` over `--days`, most recently updated first, leaving out their own PRs; `learn.history`: one GraphQL query per 10 PRs, a few at a time until enough reviews turn up, keeping the newest `--limit` reviews submitted inside the window) and leaves out every review Plus One posted for them (`actions.github_review_id`). Each PR becomes a record holding only the owner's own words (decision, summary, inline comments) beside the code each comment sits on, fenced in `reviewed_pr` tags, where every decision stays and comments share the room left; titles, replies, and author names stay out, since they could carry instructions. The `study` model role summarizes batches into notes (`NOTES_SCHEMA`), and the `learn` role rewrites the current rubric from them. `learn.problems` refuses a result that drops or reorders a heading, changes the `LOCKED` sections (Verdicts, Never auto-approve), names anyone whose text it read (`learn.people`), runs past 1.5 times the current length, or has a dash; the call retries once with the problems listed, then fails. Counts and the proposal's note cover only the batches that summarized. The `proposals` row (`kind = 'learned'`, no review) exists before the first model call and carries `cost_usd`, which `Store.spend_today` adds to the day's stages, as it does for every rubric proposal. It is accepted only by the owner after seeing the diff (in the terminal, or Rubric changes in the web app). After each GitHub sync, `actions.learn_from_github` drafts a rubric proposal (`kind = 'github'`) for each review graded wrong from the owner's own GitHub review in the last 3 days, up to `limits.auto_proposals_per_day`. It claims them in one `BEGIN IMMEDIATE` transaction, and the partial unique index `proposals_one_github` allows one per review, so two syncs at once can't both draft one. `calibrate.grade` keeps a grade's `at` while the grade and tag hold, so a sync finding the same answer again doesn't make an old disagreement look new.

### Model calls (`plus1/claude.py`)

Every call is headless `claude -p` with `--json-schema` structured output (schemas in `prompts.py`), `--restricted` so no settings file (user, project, or local) can add allow rules, the login from `claude_config_dir` when set (else the owner's normal Claude login), hooks and MCP disabled, a read-only tool allowlist plus denylist, and an environment with GitHub credentials stripped (`GH_CONFIG_DIR` points at an empty dir). After any change to `ALLOWED`, `DENIED`, `_env`, or the CLI flags, rerun `tests/selftest_sandbox.py`. Searching goes through the Grep and Glob tools because `rg`, `fd`, and `git grep` each take a flag that runs a command (`--pre`, `-x`, `-O`), and `git log`, `git show`, and `git diff` are denied `--output`. Claude Code refuses `cd` and `git` in one command, so the reviewer reads a peer's history by running `cd` into it on its own first. Model, effort, budget, and timeout per role live in `[models.*]` (`plus1/defaults.toml`, overridable per person).

### Fail closed

`Reviewed.verdict` starts as `DEFER`. `APPROVE` needs zero surviving findings and `coverage == "thorough"`, and the `never_approve` lane turns a clean result into `DEFER` with reason `"clean, but …"`. The reviewer prompt asks for its real verdict in that lane, and `words.clean_defer` leads the card with Approve only for that reason paired with a stored reviewer verdict of `APPROVE`, so a reviewer's own `DEFER` there never reads as clean. A clean result outside that lane becomes `DEFER` with `"clean, but open comments from …"` when `waiting_on` names someone `filters.waiting_on` accepts: a human who commented, isn't the author, and whose latest review of any state isn't an approval (a `COMMENTED` review after approving can carry a new question). A bot or a name the model made up never holds an approval. `actions._head_check` refuses any post once the PR head has moved past the reviewed SHA, and every review is pinned to that SHA. Card forms carry the `review_id` they were rendered for, and `routes.card_action` refuses a mismatch or an action outside `ALLOWED` for the card's state, so a stale page can't act on a newer review. `cli.handle` retires drafts still queued from earlier reviews of the PR, because `release` posts every queued draft. New code paths should default to no action.

### Approving on its own

Off by default, and each repo turns it on by itself, since trust earned on one repo doesn't carry to another: `auto_approve = true` in its `[[repos]]` entry (`config.auto_repos` lists them), which the repo's Settings form writes. Only a timer tick approves on its own (`auto` in `cli.tick`: `--trigger timer` and not `--pr`), so Review again and `tick --pr` leave a Ready to approve card even there. Every `APPROVE` gets that card until an approval at its SHA is recorded (`cards._approved`). `calibrate.stats(store, cfg, repo)` grades one repo's reviews into a checklist (working days, graded approvals, zero false approvals, agreement) that Insights and the repo's Settings form show as advice; nothing enforces it. Old `mode:<repo>` meta rows and a top-level `mode` key turn nothing on. The setting only gates the timer's automatic approvals in `cli.handle` and `cli.retry_held`. CLI and web actions (`release`, `approve`, `dismiss`, card buttons) post to GitHub either way. A draft with no P0 is not blocking: `release` posts it as an APPROVE review carrying the comments, and CLI `dismiss` approves unless `--no-approve`.

### State (`<state_dir>`, default `~/.local/state/plus1/`)

- `prr.db` (`store.py`): everything the web app shows. The schema is `CREATE TABLE IF NOT EXISTS`, so a new column on an existing table needs an `ALTER TABLE` guarded by `PRAGMA table_info` in `Store.__init__` (see `observations.channels`). Schema changes stay additive, with no dropped or renamed columns and no new column older code can't insert without, since an update that rolls back runs the older code on this database.
- `state.json` (`state.py`): last decided SHA per PR, which drives the "already decided at this commit" skip. `State.forget` (called by `plus1 drop`) clears the entry to force a re-review.
- `audit.jsonl`: append-only. The daily approval cap counts its `approve_posted` lines with `actor` `timer` (lines from before the field count too), not the DB, so approvals the owner clicks don't use it up.
- `vapid_private.pem`: the Web Push signing key, created by `push.py` on first use. Replacing it orphans every existing subscription.
- `PAUSE`, `tick.lock`, `reports/YYYY-MM-DD.md`, `work/`, `no-gh/` (the empty `GH_CONFIG_DIR`).
- `peers/`: one snapshot per repo in `peers`, each its own repo and object store holding only origin's branches (fetched from the checkout, never through alternates, whose `--alternate-refs` would list the checkout's local branches and stashes).
- `web-token`: the local web app's sign-in secret (see Web app).
- `web.sock`: in tailscale mode, the target of `tailscale serve`, which only root can change. Moving `state_dir` or `web.socket` takes the web app offline until `sudo tailscale serve --bg unix:<new path>` is rerun.

### Web app (`plus1/web/`)

Stdlib `http.server` in one of two `web.mode`s (`config.load` picks `tailscale` when `web.allowed_login` is set, else `local`). `local` listens on `127.0.0.1:<web.port>` (8470), with sign-in in `plus1/signin.py` (core, since `bin/plus1 open` and setup mint codes too): a secret in `<state_dir>/web-token` (written 0600 and atomically, and never accepted when short) never leaves the state dir, and the HttpOnly session cookie is the time it was issued plus an HMAC of that time under the secret, good for `SESSION_DAYS` (30). `bin/plus1 open` mints a one-time code good for 5 minutes (its digest in the `web_login` meta row, cleared by the one request that redeems it), prints and opens the `/login?code=` link, and with `--new` replaces the secret first, which signs every browser out. Every request must name a loopback host, so a page using DNS rebinding can't reach the app, and the access log redacts the code. Browsers send localhost cookies to every port, so another server on the same machine that the browser visits receives the session cookie; the owner's other local servers are trusted the way their files are. The session cookie there skips `Secure`, which some browsers drop over plain http. The CSRF token there is an HMAC of the secret rather than a cookie, since every port on the host is one site to a browser and a page on another port could plant a CSRF cookie. `bin/plus1 open` opens the link through a 0600 `<state_dir>/sign-in.html` redirect page, so the code stays off the browser's command line. Web Push is off, since push services want an https contact. `tailscale` listens on a unix socket published by `tailscale serve`, and `Tailscale-User-Login` must equal `web.allowed_login`. `app.py` holds the server, the auth check (`Handler.authorize`), CSRF (cookie plus `X-CSRF-Token` header or `csrf` form field on every POST), and a regex router. `routes.py` registers handlers, and `queries.py` and `cards.py` build view data from SQLite. Templates are Jinja with htmx. `/events` is SSE tailing the `events` table. The sidebar status (`partials/status.html`, from `queries.status`) shows the next check (`queries.next_check`: the timer's next half hour on this machine's clock that falls in the working window, in the configured zone) while `units.active()` finds the timer loaded, and "Slack off since" once the latest runs failed to read Slack. Nothing there may call a Linux-only tool unguarded: the macOS CI job renders every page.

Front end, no build step: `static/app.css` holds the design tokens (`:root`, with dark values under `prefers-color-scheme`) and every component. `templates/_icons.html` is an inline SVG sprite used through the `icon()` and `status_icon()` macros in `_macros.html`. `partials/card.html` wraps the shared `partials/card_body.html` as a To do row (`<details>`, swapped as `#card-<pr>`) or as the review card (swapped as `#pane-<pr>`), so both can share a page. `inbox.html` renders `/` and any review still on To do as the list (`partials/todo_list.html`) beside `partials/pane.html`: two panes at 1100px and wider, and narrower either the accordion (`/`) or the review alone (`/review/<id>`), chosen by CSS from the `is-home` or `is-review` class on `.content`. Picking a row fetches `/partials/pane/<id>` and pushes its URL. Reviews no longer on To do render `review.html`, the same pane on its own. For a `never_approve` review, the code section leads with every file in `reviews.sensitive`; reviews stored before that column fall back to `.github/CODEOWNERS` in the `checkout` repo (`cards.sensitive_files`), which follows whatever branch is checked out there. Within its group, a PR from the owner's team sorts first (a `team` chip), then one from their other teams (`watching`), then one in their own code, with a chip per signal on its row and a sentence each on its card (`words.yours`). A stack takes its best part's rank and chip. `cards.build` works out the team at render through `team.known`, so changing the lists re-sorts To do at once. `cards.entries` groups `[n/m] (TICKET)` stacks, and `cards.ordered` is the To do order that Next and `j`/`k` on review pages follow. `refs.py` links `file:line` mentions, resolving bare file names through `git ls-files` in the `checkout` repo. `static/app.js` runs the command menu (fed by `/palette.json`), keyboard shortcuts (`j`/`k` move between `[data-nav-item]` elements), toasts, undo countdowns, the review page action bar, and live counts from `/todo-state.json`. The CSP is `script-src 'self'; style-src 'self'`, so inline `<script>` and `style=` attributes are blocked: dynamic sizes go through SVG attributes (charts, meters) or `el.style.setProperty` from JS. Inter is self-hosted as `static/inter.woff2`. Every icon in `static/` (`icon.svg`, the amber `fav-N.svg` that `app.js` swaps in as the favicon while To do has N items, and the PNGs in the manifest, `apple-touch-icon.png`, and the `sw.js` badge) is generated by `uv run scripts/make_icons.py` from Inter's outlines and needs `rsvg-convert`. Edit the script, not the files.

Card actions do not run inside the request. `executor.schedule` inserts a `pending_actions` row due in 8 seconds (the Undo window), and a thread in the web process runs it through `actions.py`. An action more than 120 seconds overdue expires instead of running, one of a kind this version doesn't know is cancelled, and on startup any action left `running` is marked failed rather than retried. A failed or expired action calls `actions.notify` (desktop, plus Web Push to subscribed devices), since the page that scheduled it may be closed, and stays on its card until a newer review. A post refused because the PR has new commits starts a review of them (`executor._review_again`, through `actions.review_now`), unless a review is already running, and puts `rereview` in its `pending_actions` payload. Until a newer review row exists, for up to an hour, `cards.reviewing` counts that as running and `cards.build` hides the card, so the card and review page say it's reviewing them. When no review can start, the refusal marks the card stale, with Review again. A second thread (`cards.watch_github`) refreshes the `pr_status` table every 2 minutes with one batched GraphQL query, and `cards.build` hides any card whose PR is merged, closed, approved, or in the merge queue. To do and the watcher look back 14 days, and further for any PR whose last known state is open, so an open PR keeps its card until it merges, closes, or is handled. A card with queued drafts outlives everything else, however old its review. While the PR is open and approved by someone else or in the merge queue, a blocking draft leads To do as Approved without your blocking comment, and a non-blocking one is flagged. Once the PR merges or closes, nothing is left to act on: the card goes, and `Store.expire_unposted`, run after each status poll (never before it, since a stale closed state would expire comments on a reopened PR), marks its drafts `expired`, left ungraded, which Activity shows as Merged (or Closed) before you posted. The watcher sends a "Comments not posted" notification when such a PR moves on (only on the transition, so it fires once). Ticks can't do this because merged and approved PRs drop out of `gh.candidates`. Longer work ("review now", rubric proposals, Write it up) runs `bin/plus1` in the background through `host.spawn`: a transient `systemd-run --user` unit where systemd runs, else a detached process logging to `<state_dir>/logs/`. Desktop notifications go through `host.notify` (notify-send on Linux; terminal-notifier, else osascript with the text passed as arguments, on macOS).

`/grade` runs a grading queue: `GRADE_QUEUE` (12) review ids from `calibrate.queue` (approvals first in a repo whose checklist still needs graded ones, `calibrate.short_of_approvals`, then comment drafts, other approvals, and decisions left to the owner, leaving out PRs still on To do) ride in the URL as `q`, with skipped ids as `skip`, and every render rebuilds the strip and the current decision from the `grades` table, so a refresh or Back keeps the place; each graded or skipped answer swaps the card through htmx and sets `HX-Replace-Url`. Once the queue is done it sums its right calls, wrong calls with their tags, and skips, and shows what moved on the readiness checklist, keyed by each check's `key` from `calibrate.stats`. Another queue leaves out what this one skipped. The sidebar's Grade count is `queries.ungraded_count`, the same queue counted without the To do PRs, computed in `App.render` for every full page.

A follow-up review with no new drafts becomes a Fixed since you asked card (every ask fixed, Approve leads) or a Waiting on fixes card (Keep waiting leads, Approve anyway beside it); a `FOLLOWUP_UNCHANGED` review shows no card. Each lists the owner's asks with links to their threads. Every approval from a follow-up (`actions.approve_followup`, approve without comment, approve anyway, or an `APPROVE` release) resolves the owner's threads the review found fixed and nobody had resolved yet, through `gh.resolve_thread`, and records each as a `resolve_thread` action; open ones stay. While any ask is still open, `release_payload` posts a draft with no P0 as `COMMENT` instead of `APPROVE`, so new comments don't lift the block.

A Needs a look card lists the findings the verifier dropped (`findings.verified = 0`, leaving out `carried` ones that are fixed since the last review), with its reason. Write it up (`actions.write_up`) inserts a `writing` draft and spawns `bin/plus1 write-up <draft_id>`, which drafts through the same drafting and fact-check path as a tick and flips the row to `queued`, or to `superseded` when a newer review of the PR exists, or to `failed`. The partial unique index `drafts_one_writer` allows one `writing` row per finding, and `Store.finish_write_up` queues in one statement that only touches a row still `writing`. A writer quiet for `WRITING_MINUTES` counts as failed, and a retry marks it failed in the table, so if it finishes late it changes nothing. Every card action the executor runs retires the PR's writers (`Store.retire_writers`), so a comment can't land after the owner finished with the card. A review's `cost_usd` covers its tick, and `queries.late_spend` counts any model call after the review finished (a write-up) on the day it ran. The card polls `/partials/card/<pr>` while it writes. Once queued, the draft turns the card into Worth fixing or Must fix by its severity, and its "why" says the owner overruled the double-check.

Rewrite (`actions.rewrite`, beside Edit on every queued draft with a finding, `r` on the focused card) takes the owner's suggestion, typed or from the Shorter, As a question, and Softer chips (which add to the box with JS and submit their own text without it), and spawns `bin/plus1 rewrite <rewrite_id>`. `drafts.rewrite_comment` revises the comment as it stands through the drafting path a tick uses (the `draft` role or `draft_command`, the dash retry, the fact-check), with the diff hunk at its line (`diffs.around`) in `pr_code` tags and the current text in `current_comment` tags, both stripped of every tag these prompts fence data in (`prompts.QUOTE_FENCE`). The owner's suggestions join the facts, so a claim from them is backed, and they win over the format rules and length but never the no-dash rule or the label. The result waits in the `rewrites` table as a proposal under the comment, flagged like any draft: Use this (`Store.use_rewrite`, one transaction) takes its text, flags, and suggestion chain (`drafts.notes`), Keep mine drops it and any revision still being written, and Rewrite again revises the proposal, carrying the chain. The partial unique index `rewrites_one_writer` allows one `writing` row per draft, `Store.finish_rewrite` makes it `ready` in one statement only while the draft is queued (and the proposal it revised `revised`), a writer quiet for `WRITING_MINUTES` counts as failed, and `Store.retire_writers` retires open rewrites too, so a card action acts on the text the owner sees. The card polls `/partials/card/<pr>?rewrite=<id>`, which answers 204 until the rewrite lands, and `app.js` holds back the swap of any `data-poll` element while a textarea on the card has unsaved text, so words typed meanwhile aren't wiped. Restore original puts back `original_body` with the first draft's flags (`original_needs_edit` and `original_unsupported`, set wherever a draft is queued; older drafts count as flagged when their first fact-check listed anything) and retires any rewrite still open. Once a rewrite is used, Make this a rule (`actions.make_rule`) drafts a `kind = 'rewrite'` proposal from the owner's note and the first and kept text as they stood at the click (`proposals.comments`), with the `verify` role. `propose._run_rule` limits it to the `## Comment format (drafts)` section (`drafts.VOICE`): an edit outside the section, a new or changed heading, or a dash fails it, and its edit is the whole section, so `accept` applies it only while that section is unchanged. `proposals_one_rewrite` allows one pending or ready rule per draft.

### Reason strings are an interface

`web/words.py` turns stored reasons into UI copy by matching the exact text produced in `filters.py` and `review.py` (`"X is owned by Y"`, `"X matches a restricted path"`, `"too large to trace (N changed lines)"`, `"thin coverage: "`, `"findings did not survive verification: "`, `"clean, but "`, `"clean, but open comments from "`, and `review.FOLLOWUP_UNCHANGED` and `review.FOLLOWUP_OPEN`, which `words` imports), plus `actions._head_check`'s `"has new commits (X is now Y)"`, which `words.HEAD_MOVED` reads. Change one side and the other silently falls back to the raw string, so edit them together and extend `PlainWordsTest`.

### Settings page (`plus1/settings.py`, `/settings`)

Edits the personal config.toml in place with tomlkit, so the owner's comments and layout survive. The page groups settings by what they do (Checking, Approving on its own, Reviewing, Notifications, System) under a status strip whose switch posts `/pause` or `/resume`, with a section rail at 1200px and wider and a grouped index plus sticky crumb below that. Each editable section is its own form posting to `/settings/<section>` (`schedule`, `sources`, `skips`, `budget`, `every`, `limits`, `models`, `repos`, `notifications`, `you`, `web`, `files`, `updates`), `/settings/rubric-limits` (proposals a day, since `POST /settings/rubric` is the rubric editor), or `/settings/repo/<n>`, whose action ends in the section's `#anchor` so a refused save comes back scrolled to it. `settings.parse` validates one section into `{(scope, table, key): value}`, where scope is `None` for the top of the config or a repo's name for its `[[repos]]` entry and a model role's table is dotted (`models.deep`), and `settings.changed` keeps only what differs from the loaded config, so a save touches nothing else. `settings.save` writes it, takes a top-level key set back to its `defaults.toml` value out of the file (dropping tables that leaves empty) so later default changes reach it, keeps the previous file as `config.toml.bak`, and puts that back if the result doesn't load. The schedule form asks for the hour checks stop (`end`), one past the stored `end_hour`, which `in_window` treats as the last hour checks run in. Lists kept per scope post as their plain name for every repo (the top of the config) and as `<key>@<repo>` for one repo (`settings.scoped`), named by repo so a repo added by hand meanwhile can't shift them, and only the scopes the form names change. `filters.approval_gates` isn't additive, so the page edits only the top-level list (the defaults' when unset) and names any repo that sets its own (`settings.gate_overrides`). A repo form carries its repo's name, and a mismatch with the repo at that index is refused. A `SettingsError` names its field, which the page shows under that row. `settings.LOCK` is held from reading the file to `App.adopt`, so two saves can't interleave or land out of order, and amounts must be finite. A change that lets Plus One do more on its own (`settings.loosens`: raising one of `CAPS` or a model role's budget, turning on a repo's `auto_approve`, taking an entry out of a `GUARDS` list, adding an approval-gate pattern, or switching updates to automatic or to main) raises `NeedsConfirm` carrying a `Loosening` per change until the form carries the word `loosen`, and the page re-renders with what was typed and each change as before and after. A repo's form edits only that `[[repos]]` entry's own `auto_approve`, `hold_yours` (sent only with `hold_shown`, since an unchecked switch sends nothing, and turning it off loosens), and lists (`settings.owned`); entries from the defaults or the top of the config show as locked chips and are never copied into the entry. Anything that changes what runs on this machine (`settings.RUNS`: a repo's check commands, the drafting script, the Claude login folder) needs the word `run` as well, and the page shows each new command split into the arguments it will run with (`settings.runs`). The web app's settings and the history folder (`settings.RESTART`) take effect when the web app restarts, since `App.adopt` keeps the running ones; the page fills them from config.toml (`settings.ondisk`), and `settings.restart_pending` lists any the running app hasn't taken on, beside a Restart web app button that spawns `bin/plus1 restart-web` (`units.restart_web`, which outlives the restart it causes), and the `sudo tailscale serve` command when the socket moved. The served mode, allowed login, and socket (`settings.RETYPE`) can keep the owner out, so the form must carry each new value twice (`again_<key>`). `settings.PATHS` compare by where they point, so `~/x` and the expanded path are the same. A repo's clone must be a git checkout whose `origin` is that repo on GitHub (`settings._clone`, through `setup.matches`), which ties the hooks a review's `git worktree add` runs to the repo's own clone, so it needs no `run`. Add repo (`settings.add_repo`) appends a `[[repos]]` entry, with suggestions from `setup.suggest_repos` and `setup.find_checkout` loaded only when its panel opens (`/settings/repos/suggest`), and Remove (`settings.remove_repo`) takes one out, keeping its history and never the last. You's Commit emails edits `emails`, beside the addresses `yours.detected` found, shown locked. You's Your teams, People, and Other teams edit `[team]`, lowercased on save. Saving runs `team.refresh` in a thread and waits at most `routes.TEAM_READ_WAIT` seconds for it, since GitHub can hang, and each team row shows what it last read (`team.status`). A team row's suggestions load when its panel opens (`/settings/team/suggest`: `team.suggest_mine`, or `team.suggest_others` for the orgs' teams the owner isn't on), and `settings.js` adds a picked one to the chip list. Phones and other devices live under Notifications, and `/devices` redirects there. Every save logs a `settings` action whose payload holds each changed key (`settings.key_name`) with its new and previous value, which Recent changes reads through `queries.settings_log` and `words.setting_change`. `static/settings.js` reads each field's `data-saved` to tell what's unsaved (so a page sent back after a refused save still knows), shows Save and Discard only for a changed section, checks fields before posting, marks values that differ from `defaults.toml` with a Reset, draws the schedule and 14-day spend charts, runs the chip and Slack editors over the textareas the forms post, follows scrolling in the rail, filters rows, and saves on ⌘S; `static/noscript.css` shows the plain fields and Save buttons without it. The web app takes on a saved config in place (`App.adopt`, keeping `state_dir` and `web`, which need a restart, and re-registering repos so one added by hand has an id at once), and `App.refresh_config` reloads config.toml on the next request whenever its mtime changes, so hand edits apply too; one that fails to load (a TOML syntax error is a `ConfigError` too) keeps the last good config, and the settings page says so and saves nothing until it's fixed. `/settings/rubric` previews a hand edit as a diff and saves it as an accepted `manual` rubric change (`propose.save_edit`), revertable under Rubric changes. The editor carries the version it opened (`propose.version`), so a save from an older copy is refused, and an edit whose row can't be recorded is written back; Learn again spawns `bin/plus1 learn`, which leaves its result as a proposal.

### Keeping itself up to date (`plus1/updates.py`)

`updates.mode` is `automatic` (the default), `ask`, or `off`, and `updates.channel` is `releases` (the newest `vX.Y.Z` tag on main, by version) or `main`. `updates.maybe` runs from a web app thread (`updates.watch`, every 10 minutes) and at the end of a timer tick, once it has let go of `tick.lock`. It checks at most hourly (`updates.check`: `git fetch`, then `current`, `available`, `blocked`, or `skipped` in the `updates_state` meta row; a failed fetch keeps what's known), and in automatic mode starts `bin/plus1 update --auto` through `host.spawn` when nothing is in progress (`updates.busy`: `tick.lock`, a pending card action, a comment or rewrite being written, a rubric change being drafted, each counting only while recent, so a crash can't hold off updates forever). `updates.blocked` refuses a clone that isn't on main or has uncommitted changes to tracked files, and `_where` one with commits that aren't on main. It never stashes or discards anything, and says so once (`_tell`, in automatic mode). Git runs with prompts off, since nothing can answer them.

`_install` holds `tick.lock` throughout: `git merge --ff-only`, `bin/ensure-venv`, the smoke test (`bin/plus1 --version` and `bin/plus1-web --smoke`, which run the new code: every template compiles and To do builds from the real history), the restart (`_restart_quietly`, since a restart fails whatever the web app is doing: `updates.restarting` makes `executor.run_due` leave new card actions pending for the new process, and it waits up to `QUIET_WAIT_S` for running ones; one that won't finish raises `StillRunning`, which puts the files back without blaming the version and tries again later), then `_healthy` waits for `/healthz` (`ok <build>`, where `updates.build` is the commit this process started on) to name the new commit, signing in the way the web mode expects (`updates.serving`). Any failure goes back with `git reset --keep`, restarts the old code if the restart had begun (this one insists, since the app has to come back), puts the commit in `updates_skip` so automatic mode leaves it alone until a newer one exists, adds to `updates_history`, and notifies. A successful install only gets the toast. `bin/plus1 update` waits for its moment and overrides a skip, and `--rollback` returns one step to `updates_previous` and skips what it left, refusing a clone with commits that aren't on main, which going back would drop. Going back works because the schema only adds tables and columns. `_catch_up` restarts a web app whose clone was pulled by hand.

Open pages carry their build and version in meta tags. `app.js` asks `/healthz` every 60 seconds, when the page regains focus, and 5 seconds after `/events` drops. A new build reloads the page unless something's unsaved (a changed field, a dirty Settings section, an open dialog), which shows `.update-pill` instead. `localStorage` remembers the version, so the first page after a change says Updated to or Back on, linking to `/whats-new` (`updates.changelog` reads `CHANGELOG.md` from this clone, since the repo may be private, keeping features, fixes, performance, and breaking changes). `updates.intro` shows a sticky notice once per install, and `updates.note` is the sidebar's Update available or Updates paused. Settings, System, Updates holds the mode, the channel, what's installed and latest, Check now (on a thread, waiting at most `routes.UPDATE_CHECK_WAIT`), Install, Roll back, and the history. `tests/config.toml` sets the mode to `off`, since a timer tick in a test reaches `updates.maybe`.

### Files rewritten at runtime

- Personal `config.toml`: the settings page rewrites the keys it owns (see Settings page), keeping `config.toml.bak`.
- Personal `rubric.md` (`cfg.rubric_path`, beside the personal config): the owner's whole rubric, embedded in the reviewer system prompt through `config.rubric_text`. The owner starts it from `plus1/starter_rubric.md`, and a missing one is a `ConfigError`, never a quiet fallback that would review with someone else's rules. Accepted proposals and hand edits from the settings page (`propose.py`) rewrite it (an empty `find` appends), and revert refuses if it changed since. `drafts.voice_rules` extracts the `## Comment format (drafts)` section up to the next `## ` heading or the end, so renaming that heading silently drops the voice rules from every draft.

## Tests

`unittest` with no mock library. Tests call `config.load()` (the fixture `tests/config.toml`), then point `cfg.state_dir` at a temp dir and set `cfg.notify = False`. GitHub and spawn calls are stubbed by reassigning module attributes (`gh.run`, `gh.post_review`, `gh.head_sha`, `actions.review_now`) and restored in `tearDown`. `test_web.py` runs a real `TcpServer` on an ephemeral port, sends the `Tailscale-User-Login` header and CSRF token, and advances the undo window with `executor.run_due(now_ts=...)`.
